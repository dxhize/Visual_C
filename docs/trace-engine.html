The Trace Engine: how Visual C records a running C program

The trace engine (c-trace-engine) is the part of Visual C that actually runs a student's C program and turns what happens into one detailed, replayable file — the trace. Everything the future Visual C interface shows (the C view, the assembly view, memory, pointers, the heap, crashes) is read back from that file. This page explains what the engine does and what the trace contains, in plain language.

1. What the trace engine is¶

Visual C is an offline-first learning tool: a student writes a small C program, and Visual C shows them how it really executed — statement by statement, instruction by instruction, allocation by allocation. The trace engine is the command-line component that makes this possible.

In one sentence

Compile the program, run it once under a debugger, and record everything observable about that single run into a versioned JSON file — the trace.

Three principles guide every design decision:

  • Real execution only. The engine never simulates loops or invents instruction events. If something is not in the trace, it was not observed.
  • One timeline. The C-level view and the machine-instruction view come from the same debugger run, so they can never disagree about what happened.
  • Honesty about gaps. Whenever data could not be observed (timeout, limit, unreadable memory, optimized-out variable), the trace says so explicitly instead of guessing.

2. The big picture¶

Your C sourcesone or more .c files, plus build settings

→

→
The trace (JSON)one file describing the whole run

The compiler, debugger and analyses are real external tools (GCC, GDB, Valgrind, addr2line). The engine drives them, enforces time and memory budgets, and stitches their outputs into one coherent document.

3. What happens, step by step¶

  1. Compile. Every translation unit is compiled with debug info (-g -O0). Compiler errors are captured in a machine-readable form and end up in the trace, so even a failed build produces a useful partial trace. A small runtime is linked in that records every malloc/calloc/ realloc/free the program makes to a side file.
  2. Run under GDB. The engine launches GDB in its machine-facing mode (MI2), breaks at main, and steps through the student's code — instruction by instruction in dual mode, or line by line in the cheaper source-only mode. Program output is captured through a separate channel so it never mixes with debugger chatter.
  3. Record at every stop. Each time the program pauses, the engine records where it stopped (file, line, function, call stack), every visible variable (name, type, value, its own address, and for pointers the address it points to), the live contents of heap blocks, and the program's output so far. In dual mode each attempted machine instruction is recorded too: its address, the address of the next instruction, what happened (completed, faulted, interrupted), and selected memory reads.
  4. Analyze independently. Valgrind re-runs the program on its own to hunt for memory errors with a second opinion. When triggered — a crash, or Valgrind findings — the sanitizer-built binary also runs once as a diagnostic pass. Allocation callers are resolved to file:line in one batched addr2line call.
  5. Assemble the trace. Everything is written as one JSON document with a schema version, per-stage health reports, resource usage, and honest notes about anything that was skipped or degraded.

4. A guided tour of the trace file¶

A trace is a single JSON object. These are its main sections, grouped by what a reader (and later the Visual C interface) uses them for. A full real example lives at examples/v21_dual.json.

SectionWhat it containsThink of it as…
snapshots One record per stop in the student's code: source file/line/function, the call stack, all visible variables with addresses and raw bytes, live heap-block contents, and program output so far. "A photo of the program's state" at each C statement
instruction_events
disassembly_table		 Every attempted machine instruction in order (address, next address, outcome, source line it belongs to), plus a de-duplicated table of instruction definitions (text, bytes, function) referenced by ID. "The assembly view" — what the CPU really did
heap_events
heap_state
allocation_lifetimes		 The full allocation story: every allocated/reallocated/ freed event, the final state of every block (live or freed, with contents), and each block's lifetime boundaries with stable IDs. "The memory view" — the heap's biography
crash_report For a crash: the signal (e.g. SIGSEGV), the exact source line and faulting instruction address, and a backtrace. "Why did it die?"
valgrind_report
sanitizer_report		 The independent memory analyses: Valgrind errors (with stacks and leak classification) and the sanitizer reproduction attempt, each with its own completeness flags. "Second opinions" from other tools
execution, execution_status The overall outcome: completed, crashed, timed out, hit a limit, failed to compile, and so on — with exit code and signal. "How did the run end?"
stage_results Health report per stage (compiler, debugger, Valgrind, sanitizer, allocation tracker): status, duration, and a reason whenever something did not complete. "Did each part finish, and if not, why?"
coverage, trace_gaps Which parts of execution were observed (user_code scope) and which intervals were not (program startup, skipped library code), with explicit gap records — never guessed counts. "What did we NOT see?"
resource_usage, profiling Measured consumption: wall time, number of debugger commands issued, snapshot count, which limits fired, timing breakdowns. "What did the recording cost?"
analysis_notes, session_meta, execution_limits, tracing_configuration, compile_errors, storage Everything else a careful reader needs: warnings and degradations, tool versions, the effective limits, the configuration used, compiler diagnostics, and storage/bookkeeping details. "The fine print, in the document itself"

A single instruction event, annotated

Real values from examples/v21_dual.json, annotated:

{
  "event_id": 0,              // ordered, zero-based: this is the 1st attempt
  "address": "0x0000000000400586",   // the instruction that was ABOUT to run
  "next_address": "0x0000000000400587", // actually observed next stop — never guessed
  "instruction_id": 0,         // index into disassembly_table (no repeated text)
  "source": { "line": 29, "func": "main" },
  "outcome": "completed",      // completed | faulted | interrupted | unknown
  "stopped_reason": "end-stepping-range",
  "memory": [],               // reads of user-configured watch addresses appear
                                 // here (e.g. {"expression":"&x","status":"valid",
                                 //  "raw_bytes_hex":"0a000000"}) — none configured here
  "checkpoint_id": 0           // links to the nearest snapshot (the C-level state)
  // note: no "registers" key — see the performance section
}

A single variable record, annotated

Real values from examples/v21_dual.json (the fixture's int *arr pointing into a heap block):

{
  "name": "arr", "c_type": "int *",
  "value": "0x705010",            // what the pointer CONTAINS
  "address": "0x7fffffffda48",   // where the pointer variable itself lives
  "points_to": "0x705010",
  "target": { "kind": "heap", "allocation_id": 1,
              "base_address": "0x705010", "offset_bytes": 0 },
  "raw_bytes_hex": "10507000…",  // the pointer's own bytes, as observed
  "read_status": "valid"
}

Pointer targets are classified as stack, heap (with the allocation ID it belongs to), global, code, null, unmapped or unknown — so the interface can draw "this pointer goes to that heap block" without guessing.

5. How the C view and assembly view stay in sync¶

Both views come from one run of the program under one GDB session. Every event in the assembly view carries a stop_id pair and optionally a checkpoint_id pointing into the source view's snapshots. Concretely:

  • Each recorded instruction event names the source file, line and function it was paused in — that is the link from assembly back to the C statement.
  • Snapshots (the C-level state photos) record how many instruction attempts had happened before them, so either timeline can be navigated from the other.
  • Instruction addresses are taken from the debugger's own stop reports. The next address is always the actually observed next stop — crucial, because machine code frequently does not run sequentially (branches, calls, returns, faults).
Why this matters for Visual C

The interface can highlight a C statement, show the exact machine instructions that executed for it, and step through them — all from one file, with no risk of the two views disagreeing.

6. What is exact, and what is not¶

A learning tool must never show invented data as if it were real. The trace follows a strict honesty policy:

  • Values are exact only at their recorded stop. A snapshot shows the program's state at that moment; nothing claims to know intermediate values between stops.
  • Nothing is fabricated. Unobservable data is null, with a machine-readable why: validity flags such as valid, unavailable, unreadable, optimized_out, truncated, not_captured.
  • Gaps are explicit. Startup before main, and code the engine deliberately steps over (library internals), appear as trace_gaps with observed boundary addresses — the number of unseen instructions is never invented.
  • Partial beats silent. A timeout, a limit or a crash still yields a trace containing everything captured up to that point, clearly marked as incomplete.
  • A freed block's bytes are the last bytes seen while it was alive. Memory is not read after the block was freed — the trace says so rather than implying the bytes are current.
Rule for the interface

Never present a memory value as "current" unless its record says it was observed at the displayed stop. The trace gives you the status flags to enforce this.

7. Safety limits, timeouts, partial traces¶

The engine wraps everything in budgets so a runaway student program cannot hang the session. Limits are configurable on the command line or in a JSON config file; hitting one terminates collection gracefully and keeps the partial trace.

Limit (flag)DefaultWhat it bounds
--timeout10 sThe whole session: compile + run + analyses
--max-steps1,000Debugger stepping commands
--max-memory-mb256 MBAddress space of the program being traced
--max-output-bytes1 MiBCaptured program output (ends the run as output_limit_reached)
--max-heap-allocations10,000Tracked allocation records
--max-snapshots1,000State photos
--max-snapshot-memory-bytes1 MiBVariable + heap bytes read per snapshot
--max-memory-read-bytes4 KiBA single memory read
--max-instruction-events100,000Recorded instruction attempts
--max-gdb-commands1,000,000Total debugger traffic
--max-processes16Child processes (when cgroups are available)
Not a security sandbox

These limits are not a security sandbox. They protect the session from runaway programs, not the machine from malicious ones. Real isolation needs a container or VM.

Every limit that fires is recorded in resource_usage.limits_triggered (each limit appears at most once), and the overall outcome reflects the real cause — e.g. ending because the output cap was hit is reported as output_limit_reached, not disguised as a step limit.

8. Crashes and memory errors¶

Three independent sources of truth, kept strictly separate:

  1. The debugger observes the crash itself. The trace keeps the signal, the exact faulting instruction (its address matches the last assembly event, marked faulted) and the source line. No events are invented after the crash.
  2. Valgrind is the second opinion. The program runs a second time under Valgrind's memcheck, which can catch errors that did not crash — use-after-free, out-of-bounds accesses, leaks — and reports them with stacks and source locations. Findings are correlated with the heap timeline by file and line.
  3. The sanitizer pass is the reproduction attempt. A second binary built with AddressSanitizer (plus UBSan when installed) runs on its own. What it found, and whether it truly reproduced the recorded crash, is kept separate from the debugger's observations — an ASan finding that does not match the crash is labeled diagnostic_observed, never forced into agreement.

When does the sanitizer pass run?

Configurable with --sanitizer-trigger:

ModeMeaning
neverSkip the pass entirely.
on_crashRun only when the traced run crashed (the V2 behavior).
on_crash_or_valgrind_errordefault Run on a crash, or when Valgrind found memory errors even though the program exited cleanly.
alwaysRun for every successful build, budget permitting.
Note

Valgrind and the sanitizer never run in the same process, global time budgets are always respected, and a skipped pass records the reason in stage_results.sanitizer.

9. Performance at a glance¶

The engine was profiled with a formal audit. The original design polled the CPU registers after every single instruction — useful for a register panel, but it consumed about 90 % of all debugger time. Visual C will not show register panels, so version 2.1 removed that collection entirely.

Result on the audit benchmark suite (median of 3 runs, same machine):

WorkloadBeforeAfterSpeed-up
Finite loop (1,012 instructions)19.1 s6.1 s3.1×
Function calls (1,413)28.5 s8.9 s3.2×
Heap churn (1,363)31.1 s12.3 s2.5×
Nested loops (1,352)29.9 s13.3 s2.2×
Recursion (671)20.0 s10.1 s2.0×
Simple arithmetic (18)3.6 s3.8 s— (fixed startup cost dominates)
See also

Instruction addresses were never taken from registers — they come from the debugger's stop reports — so nothing about the recorded execution changed. The same audit confirmed the remaining big cost is capturing the C-level state photos, which is the core educational feature and stays. Full methodology and numbers: docs/v2.1/performance.md.

10. Running it yourself¶

# the basics: compile, run, write trace.json, print the trace to stdout
cargo run -- sample.c

# save to a file; give the program some arguments
cargo run -- sample.c --output trace.json --  --verbose 42

# common knobs
cargo run -- sample.c --timeout 3 --max-steps 200
cargo run -- sample.c --trace-mode source          # cheaper, C-level only
cargo run -- sample.c --sanitizer-trigger always
cargo run -- sample.c --gdb-path /usr/bin/gdb-14   # override tool discovery

# a failed build still produces a trace with the compiler diagnostics
cargo run -- broken.c
Exit codeMeaning
0A trace was produced (completed, crashed, timed out, or hit a limit are all "success" for the recorder).
2Compilation failed; a partial trace with the diagnostics is still emitted.
1Operational error (bad arguments, missing source, missing required tool). No trace.

The optional journal

With --journal run.jsonl the engine additionally streams every record (configuration, disassembly entries, instruction events, checkpoints, gaps, …) to a line-oriented log as execution proceeds, and finalizes it with a footer record. This is what allows very long runs to keep a complete, durable record even when the JSON is instructed to keep only a bounded index in memory (--journal-only).

11. Known limitations¶

  • Instruction coverage is user code only: program startup and excluded library internals appear as explicit gaps, not recordings.
  • In multi-threaded programs the engine records the selected thread's steps; a complete interleaving of all threads is out of scope (the trace marks coverage incomplete and explains why).
  • Children created by fork are not instruction-traced (their allocations may still be recorded).
  • Self-modifying / JIT code is unsupported; the disassembly cache assumes code does not change under the engine.
  • The allocator wrapper sees the program's own allocation calls; memory allocated inside libc or other libraries is invisible to the heap timeline (Valgrind still sees all of it).
  • Per-instruction CPU register values are not collected (removed in V2.1 with the feature they served). Old traces that contain them still load.
  • The trace is produced by a development machine, not a security sandbox — see the limits section.

12. Glossary¶

Trace
The versioned JSON document this engine produces — the complete, replayable record of one program run. Schema version 2.
Snapshot / checkpoint
A "state photo": the source location, call stack, variables, heap contents and output captured at one debugger stop in user code.
Instruction event
One attempted machine instruction: where it was, where execution went next, and what happened. Attempts are recorded even when they fault.
Disassembly table
A de-duplicated catalog of instruction definitions (text, bytes, function). Events reference it by ID instead of repeating assembly text.
GDB / MI2
The GNU debugger, and its machine-oriented command interface ("MI") that the engine uses to drive it reliably.
Inferior
Debugger jargon for the program being debugged.
Valgrind / memcheck
An independent analysis tool that re-runs the program and detects memory errors and leaks without a crash.
Sanitizer (ASan/UBSan)
Compiler-instrumented error detection linked into a second build of the program; used here as a reproduction pass.
DWARF
The debug information format GCC embeds in the binary; it is how addresses map back to source lines, variables and types.
Heap timeline
The ordered story of allocated / reallocated / freed events reconstructed from the program's own allocator calls.
Trace gap
An explicit record of an interval that was deliberately or necessarily not observed (startup, skipped library code), with observed boundary addresses.
Stage result
Per-stage health report (compiler, debugger, Valgrind, sanitizer, allocation tracker): completed, failed, timed out, skipped or cancelled — with a reason.
Journal
The optional line-by-line log the engine writes while running; enables durable recording and memory-bounded operation.
